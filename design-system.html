Long-form article

2026 · Notes

On restraint in a busy design system

The temptation with any component library is to grow it — but growth is the enemy of consistency. Every new component is a decision every consumer has to relearn, and the marginal value of the tenth badge variant is almost always negative.

The most useful thing a design system can do is stay small enough to hold in your head. This one has around twenty components, five type sizes, a single 4-px base grid, and one accent colour. That's enough for a personal site, a set of experiments, and the occasional editorial piece — and it's few enough to review in an afternoon.

How to apply this to the site

Docs

1. What we're replacing

Today, src/styles/system/ mixes:

  • The full Google Material colour palette (256 variables you never use)
  • SCSS mixins that emit debug mixin: name properties
  • Component styles inlined into _elements.scss and _type.scss
  • .text-center that resolves to text-align: left (see mixins/_grid.scss)

The new system replaces all of it with tokens on :root plus a small component sheet.

2. File layout

├── system/
│   ├── tokens.scss           // :root { --color-… --space-… --fs-… }
│   ├── reset.scss            // element normalizer

│   ├── layout.scss           // .container, .grid, .col-*, .stack

│   │   ├── card.scss
│   │   ├── form.scss

3. Migration steps

  1. Copy the :root block from this page into src/styles/system/tokens.scss.
  2. Delete variables/_colors.scss (the Material palette) and variables/_palettes.scss.
  3. Point palette--primary-* callers to the new CSS variables via a compatibility shim (one week), then remove.
  4. Delete the mixin: name; debug declarations from every mixin.
  5. Replace @include button-link etc. with the .btn component classes in EJS templates.
  6. Change the grid mixin's grid-template-columns: repeat(4,1fr) mobile / repeat(12,1fr) desktop to also add an 8-col tablet tier at 600px.
  7. Fix text-center and text-left in mixins/_grid.scss — both currently emit text-align: left.

4. How to use a token

Always reference the CSS variable, never the raw value:

/* ✅ good */
.my-card {
  background: var(--color-surface-1);
  padding:    var(--space-6);
  border-radius: var(--radius-md);
}

/* ❌ bad */
.my-card { background: #12161C; padding: 24px; border-radius: 12px; }

5. How to build a new component

Every component defines its own tokens on the block, then references them internally. That makes it trivial to theme, subclass, or override:

.btn {
  /* component-owned tokens — override these to reskin */
  --btn-bg: var(--color-surface-2);
  --btn-fg: var(--color-text);
  --btn-border: var(--color-border);

  background: var(--btn-bg);
  color:      var(--btn-fg);
  border: 1px solid var(--btn-border);
}
.btn--primary { --btn-bg: var(--color-primary-500); --btn-fg: var(--color-text-inverse); }

6. Grid — worked example

The homepage's .deck becomes:

<div class="container">
  <div class="grid">

7. Accessibility checklist

  • Every interactive element has a visible :focus-visible ring via --focus-ring.
  • Tap targets are ≥44px on all buttons, links, checkboxes, and radios.
  • Text tokens meet WCAG AA on --color-bg.
  • Motion respects prefers-reduced-motion.
  • Nav, tabs, accordion, and modal all wire up aria-* attributes and keyboard support.

9. Class-name convention

BEM-lite: .block, .block__element, .block--modifier. Utility classes (.mt-4, .text-muted) stay one word and don't take modifiers.

10. Not in this system (yet)

  • Light mode — dark is canonical. A light theme can layer as an override on html[data-theme="light"] later.
  • Data-viz palette — the /posts/* canvas experiments keep their own local scales.
  • Icons — decide between an inline SVG sprite or a small icon component before adding.
